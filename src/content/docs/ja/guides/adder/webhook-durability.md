# 再起動安全なWebhook配信

`plugins.output.webhook.state-path`に永続SQLiteファイルを設定すると、出力のキューに入ったWebhook配信を再起動後も保持できます。

```yaml
output: webhook
plugins:
  output:
    webhook:
      url: "https://example.org/adder-hook"
      format: "adder"
      state-path: "/var/lib/adder/webhook.sqlite"
      max-pending: 1024
```

`state-path`を設定すると、Adderは各イベントを1回だけ整形し、リクエスト本文をSQLiteに追加してから送信します。追加処理には[SQLiteトランザクション](https://www.sqlite.org/lang_transaction.html)を使用します。HTTP `2xx`応答を受け取ると、出力はそのエントリを明示的に削除します。HTTP `2xx`応答は、[HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)に従って受信側がリクエストを受け付けたことを示しますが、受信側の後続処理が完了したことは証明しません。再起動時、`Start`は保留中のエントリを元の順序で再生してから戻ります。再生を完了できない場合、起動は失敗し、保留中のエントリはSQLiteに残ります。

永続モードでは、`POST`を本文のない`GET`に変更するリダイレクトを拒否します。`307`および`308`リダイレクトではリクエスト本文を保持できます。

既存の再試行ポリシーは各配信実行に適用されます。最初に1回試行し、一時的な失敗に対して最大3回再試行します。終端応答または再試行上限の消化によって配信できない場合、出力は終端失敗を報告してパイプラインを停止し、エントリをSQLiteに残します。同じURLと`format`で再起動すると、そのエントリを再試行します。通常の停止処理では、出力バッファーにすでに受け入れられた後続イベントを永続化します。プロセスがクラッシュすると、SQLiteへの追加前に上流にあったイベント、パイプラインまたは出力チャネル内のイベントを失う可能性があります。このオプションは、chainsyncカーソルとWebhook追加処理を1つのアトミックなトランザクションにはしません。

キューには`max-pending`エントリ数のハード上限があります。最小値は`11`、デフォルトは`1024`です。エンコード済みのエントリごとの上限は`16 MiB`です。`state-path`にはディスク上のSQLiteファイルを指定してください。インメモリデータベースは使用できません。通常のファイル名を指定してください。SQLite URIとDSNクエリパラメーターは拒否されるため、設定によってキューの保存方法や耐久性を変更できません。

状態ファイルは、他のローカルユーザーが変更できないディレクトリに配置してください。Unixでは、Adderが各パス構成要素の所有者と権限を確認し、直近の親ディレクトリがシンボリックリンクの場合は拒否します。`/tmp`のようなroot所有のスティッキーな祖先ディレクトリは使用できます。Adderは、データベースと既存のSQLiteジャーナルサイドカーファイルを開く前に、所有者だけがアクセスできるファイル権限に制限します。起動時の検査では、状態ファイルまたは既存のサイドカーファイルがシンボリックリンクの場合も拒否します。Unixのモード検査では拡張ACLを確認しません。別のアカウントに書き込み権限を与えないように設定してください。Windowsでは、Adderアカウントだけに書き込み権限を許可するディレクトリACLを設定してください。AdderはディレクトリACLを検証しません。

これらの検査では、Adderユーザーとして動作する別のプロセスがAdderの起動中にファイルを変更することは防げません。

キューが満杯になった場合、またはSQLiteがイベントを永続化できない場合、出力はイベントを黙って破棄せずに失敗します。保留中のエントリには自動的な有効期限がありません。`2xx`の確認応答を受け取るか、オペレーターが明示的に削除するまで残ります。配信済みのエントリは直ちに削除されます。1つの`state-path`につき1つのAdderプロセスだけを使用し、再起動時もデータベースファイルを保持してください。既存の状態ファイルに対するURLまたは`format`の変更は拒否されます。これにより、古い配信が別の宛先に送信されることを防ぎます。新しい宛先には別の状態ファイルを使用してください。

各キュー済み配信は、再試行と再起動の間で安定した`X-Adder-Delivery-ID`ヘッダーを保持します。受信側がリクエストを受け付けた後、SQLiteが確認応答を記録する前にプロセスが停止すると、再生によって同じリクエストを再送することがあります。受信側はこのヘッダーで重複排除できます。出力が提供するのは永続化されたエントリに対する少なくとも1回の試行であり、厳密に1回の副作用ではありません。ロールバックイベントは先行するブロックイベントの後にキューへ入り、先行イベントを消去しません。コンシューマーは自身の状態にロールバックを適用する必要があります。

## 復旧を確認する

1. テスト用の受信側が`500`を返すように設定し、イベントを送信します。出力が失敗し、エントリがSQLiteファイルに残ることを確認します。
2. 受信側が`200`を返す状態で再起動し、同じ`X-Adder-Delivery-ID`を受信することを確認します。
3. 次のSQLでSQLiteファイルを照会し、結果が`zero`になることを確認します。

```sql
SELECT COUNT(*) FROM queue WHERE name = 'webhook.pending';
```

パッケージテストは、外部サービスを使用せずに、この手順、バッファー済みイベントの正常な永続化、宛先の識別情報、順序を保ったSQLite再生を検証します。
