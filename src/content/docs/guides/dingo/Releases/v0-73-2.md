## v0.73.2

**Title:** Improve recovery, governance reporting, and database efficiency

**Date:** 2026-09-27

**Version:** v0.73.2

**Release:** [v0.73.2](https://github.com/blinklabs-io/dingo/releases/tag/v0.73.2)

This release improves rollback recovery, ledger replay, VRF key reservation, deferred metadata restoration, governance voting power reporting, and batched UTxO deletion.

### Recommended Network Compatibility ⚠️

| Network             | Compatible |
|---------------------|------------|
| mainnet             | ⛔         |
| preprod-testnet     | ✅         |
| preview-testnet     | ✅         |
| musashi             | ✅         |

### Recovery, governance, and database improvements

* Improved reward precompute recovery after rollbacks by clearing stale work in progress, restoring or requeuing valid replacement work, and rejecting retries from older generations. Dingo now serializes precompute writes with rollback truncation and invokes `FatalErrorFunc` when it cannot commit the durable tip floor; reward arithmetic and schemas remain unchanged.

* Corrected ledger recovery precedence by comparing complete chain points, including the slot, hash, block ancestry, and block number, rather than the slot alone. Valid predecessors at the same slot can now take part in recovery, preventing replay from becoming stuck.

* Refined VRF key reservation within an epoch so only the latest registration for each pool reserves a key. Dingo now frees superseded intermediate keys and aligns ledger validation with the reference behavior.

* Restored missing deferred metadata indexes during restore and startup, with cancellation support and progress logging. When no bulk load marker is active, Dingo rebuilds the complete manifest.

* Expanded DRep voting power for ratification, `LedgerView`, and Blockfrost reporting to include active governance proposal deposits. Dingo now handles expired return accounts and excludes `AlwaysAbstain` from this deposit based voting power.

* Optimized batched UTxO deletion by looking up `tx_id` through its index before updating rows by primary key. SQLite avoids scan prone query plans while other databases retain their locking and liveness guards.
